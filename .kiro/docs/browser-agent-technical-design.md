# Browser Agent 技术方案

> 状态：设计基线。实现以本文为准；代码与本文不一致的地方按本文调整。

## 1. 它要成为什么

Browser Agent 让用户对着聊天框说一句「把我这些标签整理一下」，然后得到一个整理好的浏览器。
标签、标签组、收藏夹三类对象，AI 负责分类和命名，扩展负责把方案变成真实操作并保证可退回。

它**不做**：网页正文/元数据抓取、修改 `document.title`、任意 SQL、浏览器现场保存恢复。
Data Agent 的工具在这里不可见，反之亦然。

**标签备注推迟。** 一个只有扩展界面看得见、绑在标签 id 上、浏览器重启就失效的备注，
恰好在用户需要它的时候（下次找这个标签）不存在，却要占一个写操作、一次批准、一条账本记录和一条恢复路径。
它重新进入范围的条件是找到稳定的载体：绑到 URL 上持久化，或者用 Firefox 的
[`sessions.setTabValue`](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/sessions/setTabValue)
这类跨重启存活的通道（Chrome 无对应能力，所以它只能是增强，不能是基线）。

### 主线（读完这一节就知道整个功能长什么样）

```
用户在 Gemini/AI Studio 输入框打 > 选「整理标签页」
  ↓
AI 调 browser_list_tabs → 拿到当前窗口 84 个标签（标题 + URL + 组关系 + 重复标记）
  ↓
AI 出方案，一次 browser_arrange_tabs + 一次 browser_manage_tab_groups
  ↓
扩展生成预览（不是操作清单，是「整理后的样子」）：
    新建 4 个组：文档(蓝) 12 · 待读(黄) 23 · 工作(绿) 9 · 购物(粉) 5
    移出组：3 个标签
    保持不动：32 个标签
    ⚠️ 无
  ↓
用户点批准（这批全是无损操作 → 可以选「本次任务不再问」）
  ↓
扩展逐步执行，每步只校验这一步涉及的对象没被改动
  ↓
结果回传给 AI：4 组已建，49 个标签就位，0 失败
  ↓
AI complete_task；侧边栏留一条本机记录，整理前和整理后两个状态都能一键回去
```

有损操作（关闭标签、删除收藏夹）不在这条主线上，走 §6 的独立路径。

⚠️ 这一节是其余所有约束的锚。任何一条规则如果不能说清它在保护上面哪一步，就不该存在。

## 2. 浏览器支持

Chrome 和 Firefox 同一套代码，**按运行时能力探测，不按 build target 分叉**。
`import.meta.env.BROWSER` 只用来决定 manifest 里申请哪些 optional permission。

| 能力 | Chrome | Firefox | 探测方式 |
|---|---|---|---|
| 标签读写 | 88+ | 109+ | `browser.tabs.move` 存在 |
| 会话标识（epoch） | 102+ | [115+](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/storage/session) | `browser.storage.session` 存在 |
| 收藏夹读写 | 88+ | 109+ | `browser.bookmarks` 存在 |
| 分组 / 取消分组 | 88+ | [138+](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/tabs/group) | `browser.tabs.group` 存在 |
| 组属性（读、改名、改色、折叠、移动组） | 89+ | [139+](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/tabGroups) | `browser.tabGroups` 存在 |
| 恢复已关闭标签 | 37+ | [52+](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/sessions/restore) | `browser.sessions.restore` 存在 |

结论：Firefox **139+ 全功能**，138 只差组属性（此时整组能力一起隐藏，不做半残的分组），
115–137 只有标签和收藏夹能力，115 以下 Browser Agent 整体不可用并提示升级。
manifest 的 `strict_min_version` 保持 109 不变 —— 门禁在运行时，不在安装时。

⚠️ 探测的是**函数是否存在**，不是版本号。版本号会因为渠道和 backport 说谎，
而 `optional_permissions` 里写了一个宿主不认识的权限，整个 manifest 会被拒。
Firefox 的 `tabGroups`、`tabs`、`bookmarks`、`sessions` 都在
[官方可选权限清单](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/optional_permissions)
里，所以 `optional_permissions` 两个浏览器写同一份。

⚠️ Firefox 授予 `tabGroups` 是**静默**的（不弹窗），`tabs` / `bookmarks` / `sessions` 会弹。
所以权限设置页不能假设「点了就一定有弹窗」，一切以 `permissions.contains()` 的回答为准。
另外 Firefox 要求 `permissions.request()` 来自用户手势 —— 独立设置窗口里的点击满足这一条，
后台自发申请不满足，这也是权限入口必须是独立页面而不是 AI 能触发的动作的原因之一。

跨浏览器的**行为**差异（不是 API 有无）集中在 §12，那些差异会影响预览里的承诺措辞。

## 3. 能力与权限

能力默认全部关闭，由用户在独立设置窗口逐项点开。前端只注入已授权的工具，
后台在 prepare 和执行每一步时重新核对 `permissions.contains()` 和能力开关。
隐身/私有窗口的对象一律不返回、不可操作。

| 能力 | 浏览器权限 | 能做什么 | 档位 |
|---|---|---|---|
| `tabs.read` | tabs | 标题、URL、窗口、位置、固定、组关系、重复标记 | 读 |
| `tabs.arrange` | tabs | 排序、移窗口、固定/取消固定、激活、新建标签 | 低损 |
| `tabs.close` | tabs（+ sessions，随 §6 的 `sessions.restore` 一起申请） | 关闭标签，以及恢复自己关掉的标签 | 有损 |
| `tabGroups.read` | tabGroups | 组的标题、颜色、折叠状态、位置 | 读 |
| `tabGroups.write` | tabGroups | 分组、取消分组、改名、改色、折叠、移动组 | 低损 |
| `bookmarks.read` | bookmarks | 读取和搜索 | 读 |
| `bookmarks.arrange` | bookmarks | 新建、重命名、移动 | 低损 |
| `bookmarks.delete` | bookmarks | 删除 | 有损 |

⚠️ 能力 id 的**前缀就是浏览器权限名**（`tabs` / `tabGroups` / `bookmarks`），
`permissionsFor()` 直接由前缀推出要申请哪个权限。所以组能力叫 `tabGroups.*` 而不是 `groups.*`：
省掉一张「能力前缀 → 权限名」的映射表，也让「改了能力名却忘了改权限名」这类错不可能发生。

依赖关系（勾选时自动带上，取消时自动收回下游）：

```
tabs.arrange    → tabs.read, tabGroups.read
tabs.close      → tabs.read, tabGroups.read
tabGroups.read  → tabs.read                    （组只有配上成员才有意义）
tabGroups.write → tabGroups.read, tabs.arrange
bookmarks.*     → bookmarks.read
```

⚠️ 标签侧的两档都带上 `tabGroups.read`，因为标签批次的快照要记组关系：
一个标签被移进/移出组，如果快照里没有 `groupId`，这个变化既描述不出来也退不回去。
（代价是「只想让它排排序」的用户也要授 `tabGroups` 权限；Chrome 授这个权限不弹窗。
Firefox 138 以下没有 `tabGroups`，届时按 §2 的探测让标签能力也一起隐藏。）

⚠️ `tabs.close` 单独成一档而不是并进 `tabs.arrange`，是因为它是标签侧**唯一**真正有损的操作，
而它恰好也是「整理」这个词最容易被理解成的动作。把它和「换个位置」放在同一个开关后面，
用户授权时无法表达「你可以整理，但别关我东西」——这是这个功能最常见的诉求。
`bookmarks.delete` 同理。

⚠️ 档位是**从能力推导**出来的，不再单独维护一张操作风险表。一个操作的档位 = 它所属能力的档位，
一批操作的档位 = 其中最高的那一档。§4 的批准规则只读这一个值。

⚠️ Chrome 侧 `tabs.arrange` 和 `tabs.close` 映射到同一个 `tabs` 权限，
所以这两档的区分是**产品闸门而非系统闸门**。文档必须承认这点：撤销 `tabs.close` 能力后，
浏览器权限可能仍然在，扩展靠自己的能力检查拒绝执行。这不降低价值（越权路径只有扩展自己），
但决定了实现上「能力检查」和「权限检查」两处都不能省。

## 4. 批准

纯读取不批准。每一次实际修改都要批准，但**批准的有效范围按档位**：

| 档位 | 范围选项 | 能被设置豁免吗 |
|---|---|---|
| 低损（arrange / tabGroups.write / 恢复） | 本批 / 本次任务 | 能：`autoRunWrites` 和 `speedMode` 对它有效 |
| 有损（tabs.close / bookmarks.delete） | 只有本批 | 不能：忽略一切自动执行开关 |

⚠️ 低损必须允许「本次任务放行」。整理 80 个标签在冲突重算后可能变成三四次提交，
每次都问一遍会让用户直接把整个保护关掉 —— 那比放行低损操作危险得多。
而低损操作的定义就是「用户看得见、扩展能完整退回、没有数据丢失」，它承受得起这个信任。

⚠️ 有损档不接受任何豁免，包括用户自己在别处点过的「本次任务不再问」。
一批操作的档位取其中最高的一档，所以「顺手关掉 5 个重复标签」会把整批拖进有损档 ——
这是刻意的：AI 不能靠把有损操作混进一批无损操作来降低它的门槛。

批准绑定的是 `planId` + 它点名的那些对象，不是「一类操作」。
宿主标签不同、plan 过期、点名的对象已经不在，一律拒绝执行并要求重新批准。

⚠️ 已经尝试过（`applying` 之后）的 plan 永远不能再次提交。要重来就重新 prepare 一个新 plan，
因为一个结果不明的执行不该有第二次机会去把状态弄得更不明。

⚠️ 被拒绝的 plan 也记进账本（`failed` + 原因，没有 after 状态）。用户批准过它，
「它没发生、以及为什么」和发生了的批次一样值得留一行。

## 5. 预览：批准的对象是结果，不是操作

预览由扩展从真实对象生成，AI 不能影响它的内容。它必须回答「我的浏览器会变成什么样」，
而不是「扩展会调用哪些 API」。

预览有两种形态，因为要批准的是两种不同的决定：

| 形态 | 批准的是什么 | 怎么呈现 |
|---|---|---|
| `operations` | AI 要求的一串改动 | 一个操作一段，逐个点名对象 |
| `restore` | 一个记录下来的状态，整体放回去 | 那个状态本身，一棵树（§11） |

```ts
type PlanPreview = OperationsPlan | RestorePlan;

interface OperationsPlan {
  id: string;
  kind: 'operations';
  count: number;                  // 操作数
  tier: 'low' | 'lossy';          // §4 的档位，UI 据此决定能不能给「本次任务放行」
  items: PreviewItem[];
}
interface PreviewItem {
  type: string;                   // close / move / create …，UI 翻译
  details: Record<string, string | number | boolean>;  // 操作参数，已解析成人话
  targets: PreviewTarget[];       // 真正会被动到的对象，最多 100 个
  targetCount: number;
}
/** 位置，不含任何 id */
interface Placement {
  window?: number;                // 第几个窗口（1 起），只有一个窗口时不给
  hostWindow?: boolean;           // 就是侧边栏所在的窗口
  group?: string;                 // 标签组名，'' = 用户没起名
  folder?: string;                // 书签所在文件夹名
  position?: number;              // 第几个（1 起）
  pinned?: boolean;
  url?: string;
}
type PreviewTarget = Placement & { title: string };

interface RestorePlan {
  id: string;
  kind: 'restore';
  tier: 'low';                    // 恢复只放回不删除，所以档位是常量（§11）
  side: 'before' | 'after';       // 恢复的是这个批次之前还是之后的状态
  tree: TreeNode[];               // 那个状态，每个节点标注这次会对它做什么
  effects: RestoreEffects;
}
/** 一次恢复落到对象上的账。`extra` 是加性语义的具体数字，必须显示。 */
interface RestoreEffects {
  restore: number;                // 会被搬回原位 / 改回原名
  reopen: number;                 // 已关闭，会重新打开地址
  create: number;                 // 已删除，会重新建出来
  keep: number;                   // 现在就是这样，不动
  extra: number;                  // 快照里没有、会原样保留的对象
}
```

规则：

- 低损段默认折叠成一行标题 + 计数，点开看对象；**有损段永远展开**，逐个列出标题和地址。
- `untouched`（本批没点名的同类对象数）必须显示。用户需要知道这次整理的**范围**，
  「84 个标签里有 32 个不动」和「只看到 52 个标签被动了」是完全不同的信息量。
  书签只数真实节点，不数树根和书签栏 —— 那些不是用户心里的「书签」，算进去只会让这个数字虚高。
- **不出现任何 id。** `tab_id`、`index`、`groupId`、书签 id 都不给人看。它们是批准绑定对象的方式，
  本身不描述任何东西——让用户去授权一个叫 `#66` 的对象，等于给他一个查不到的数字。
  对象一律用标题 + 地址指认，位置用「移到『待读』组末尾」这类相对说法。
  id 在 background 里解析（`Placement` / `TreeNode`，全量快照在手，是精确解析不是猜），
  组件只渲染名字、序数和 1 起算的位置。
  ⚠️ 窗口没有名字，只能给序数，按 window id 排序（≈ 打开顺序），保证同一张卡片里
  「窗口 2」始终指同一个窗口；**只有一个窗口时连序数都不给**，
  「窗口 1」在没有窗口 2 的时候是纯噪音。侧边栏自己所在的窗口说「当前窗口」，比任何序数都好懂。
  ⚠️ 移动的**目标**文件夹不是 target，是 `details.folder`。把它和被移动的书签并列进 `targets`，
  两者就分不出谁是谁；`create` 更是只有目标文件夹一条，卡片会声称「1 个对象受影响」然后点名错的那个。
- 标签组颜色走 `agent.browser.color.*` 翻译。Chrome 给的是英文色名，
  中文界面里夹一个 `cyan` 正是这张卡片要消灭的东西。
- 所有文案走 i18n（`agent.browser.*`，`useI18n()` + `defaultValue` 英文兜底），不在组件里硬编码中文。
  改文案只动 `src/locale/en.json`，其余语言由 hook 补齐。
  ⚠️ **背景 service worker 不产出用户文案**——它是整个项目唯一拿不到 locale 的上下文。
  预览只回结构化字段（`kind` / `tier` / `effect` 说明「该用哪句」），措辞和别的字符串放在一起。
  ⚠️ 布尔值渲染成 `✓ / —`，不为两个词加十四条翻译。
  ⚠️ `BROWSER_SHORTCUTS` 里 `title` 是 key，`focus` 不是——后者是拼进 prompt 给模型读的，
  故意保持英文。
- 恢复限制写在对应的段落上，不写在全局脚注 —— 只有关标签那段需要「无法恢复表单和滚动位置」，
  贴在有损段里用户才会读。

⚠️ 扩展的预览负责**「什么」**，AI 的 `change_summary` 负责**「为什么」**（「按站点域名归类，
文档类合并成一组」）。两者都显示，位置分开，谁都不能替代谁：程序讲不出分类依据，
AI 说不准真实数量。有损批次必须带 `change_summary`，缺失就拒绝 prepare；低损批次可选。

## 6. 有损操作走独立路径：默认不做

「整理」在用户心里通常不包含「删东西」。所以扩展给 AI 的默认路径是**把要清理的东西挪到一处，
让用户自己按删除键**：

| AI 的意图 | 默认路径 | 需要什么 |
|---|---|---|
| 关掉这些标签 | 移入「待清理」组并折叠 | `tabGroups.write`（低损） |
| 关掉这些标签（没有组能力） | 存入「待清理」书签目录，标签保持打开 | `bookmarks.arrange`（低损） |
| 删掉这个书签目录 | 移入「待清理」书签目录 | `bookmarks.arrange`（低损） |
| 真的关闭 / 真的删除 | 逐批批准的有损操作 | `tabs.close` / `bookmarks.delete` |

⚠️ 这不是给有损操作加一层包装，而是**换掉默认值**。一次整理 80 个标签，
用「移进一个折叠的组」实现的清理感和真关闭几乎一样，代价却从「不可逆」降到「再拖回来」。
真关闭仍然提供，因为总有人就是要关，但它需要单独授权 + 逐批批准，摩擦与后果匹配。

### 关闭之后怎么回来

恢复一个状态时，其中已经不存在的标签要重新打开（§11）。优先用
[`sessions.restore(sessionId)`](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/sessions/restore)
——它会连**前进/后退历史**一起还原，两个浏览器都支持；条目不在了才退回按 URL 重开。

降级链和它在预览里的措辞：

| 条件 | 行为 | 预览措辞 |
|---|---|---|
| `sessions` 可用且条目仍在最近关闭列表里 | `sessions.restore` | 「可恢复，含浏览历史」 |
| 条目已被浏览器淘汰或跨了浏览器重启 | 按 URL 重新打开 | 「只能重新打开地址，表单和滚动位置会丢」 |
| 地址不是 http(s) | 拒绝，不假装能恢复 | 「这个页面扩展无法重新打开」 |

⚠️ 措辞按**批准那一刻**的真实条件生成，不用统一的免责文案。
「可恢复，含浏览历史」和「只能重开地址」是两个不同的决定依据，混成一句话等于都没说。

## 7. 前置条件：只校验对象，不校验浏览器

**没有「浏览器整体没变」这道闸门。** 唯一的检查是「这个操作点名的对象还在，还是它当初的那个对象」，
在 prepare、commit 的 preflight、以及每一步执行前各跑一次。

| 操作 | 前置条件（全部必须成立） |
|---|---|
| 排序 / 移窗口 | 每个目标标签存在；不是宿主标签 |
| 固定 / 取消固定 | 标签存在 |
| 激活 | 标签存在 |
| 关闭 | 标签存在；**`url` 与 prepare 时相同** |
| 建组 / 取消分组 | 所有成员存在、同窗口、未被固定；不含宿主标签 |
| 改组属性 / 移动组 | 组存在；不是宿主标签所在的组 |
| 新建标签 / 新建书签 | 目标窗口或父目录存在且可写 |
| 书签改名 / 移动 | 节点存在；不是受管理或根节点；目标目录不是自己的子孙 |
| 书签删除 | 节点存在；不是受管理或根节点 |

⚠️ **只有关闭绑定字段值。** 关一个标签关的是「当时在里面的那个页面」，
标签 id 在同一会话里会复用，页面也会自己导航走 —— 用户批准放弃的是他看到的那个页面。
其它操作不比对任何字段：一个标签被移过、被固定过、加载了新内容，它仍然是那个标签。

⚠️ 这是整个方案里最容易被写反的一条。「整理标签」的典型用户开着几十个标签**并且还在用浏览器**，
整理过程持续几十秒。把「整个浏览器状态相等」当准入条件，在这个场景里等于随机失败，
而且失败率随标签数上升 —— 越需要这个功能的人越用不了。而这些变化里没有一种能让操作落到错的对象上：
对象是按 id 点名的，上面这张表就是确认 id 还指着同一个东西。

⚠️ 所以也不需要「按当前状态重算」这类补救路径，也不需要 supersedes 链。没有误报要补救。

⚠️ 全窗口快照仍然要采，但它喂的是**账本和预览**（§11），不是闸门。

新建对象的 ID 只有执行后才知道。依赖新对象的后续操作放在下一次工具调用里，用返回的真实 ID，
并单独批准。一批之内不允许引用「本批将要创建的东西」。

## 8. 位置用相对锚点，不用绝对下标

绝对 `index` 在有人同时用浏览器时必然漂移，而且漂移的后果是**静默放错位置**，不是报错。
所以工具协议里不接受绝对下标：

| 意图 | 参数形态 | 扩展做什么 |
|---|---|---|
| 这些标签按这个顺序排列 | `{type:'order', tab_ids:[...], into?: group_id \| window_id}` | 读当前位置，算出最少的 move 调用 |
| 这个组放到那个组前面 | `{type:'move_group', group_id, before_group_id?}`（都省略 = 末尾） | 算实际下标 |
| 这个书签放到那个书签后面 | `{type:'move', id, parent_id, after_id?}`（省略 = 目录末尾） | 算实际下标 |

⚠️ `order` 的语义是「这些标签在它们的容器里**按此相对顺序连续排列**」，
不是「第 3 个标签去第 12 位」。前者在浏览器状态变化后仍然是同一个意图，后者不是。
新建标签允许指定「插在某个标签之后」，同样不用下标。

⚠️ 恢复（§11）用同一个原则：按快照记录的相对顺序，从每个窗口的**游标**依次排下去，
而不是套用记录里的绝对 index。快照之后新开的标签必须有个去处，而唯一能让被恢复的标签
保持记录顺序的答案是「排在它们后面」。游标的起点跳过那些不在快照里的固定标签 ——
Chrome 强制固定标签占据窗口最前面，新固定的标签无论如何都在位置 0。

### 重复标签：识别，但不代替用户决定

`browser_list_tabs` 每个条目带两个可选字段：

| 字段 | 判据 |
|---|---|
| `duplicate_of` | 完整 URL 逐字符相同（含 query 和 fragment），指向组内 id 最小的那个 |
| `similar_to` | 去掉 fragment 后相同，或去掉 query 后相同 |

⚠️ 两个字段必须分开。`similar_to` 里躺着「同一份文档的不同章节」和「同一个搜索的不同关键词」，
把它当重复处理会丢东西。AI 可以据此建议，但**不能把 `similar_to` 当成等价**，prompt 里明写。

⚠️ 识别和删除是两件事。找出重复是「整理标签」最主要的诉求之一，必须提供；
怎么处置它们仍然走 §6 的默认路径（进「待清理」组），而不是自动关闭。

## 9. URL 与隐私

默认把完整 URL 发给当前对话。这是功能成立的前提：`https://docs.google.com/…` 分不出是哪份文档，
只给域名的话 AI 只能按站点归类，而用户想要的是按主题归类。

隐私的**主手段是排除，不是降精度**：

- 排除清单按域名（`*.bank.com`）和按窗口配置，在权限设置窗口里维护。
- 被排除的对象**完全不出现**在任何列表、预览、结果里，也不可被操作。
- 同时告诉 AI「当前窗口有 6 个标签被你的排除规则挡住了」—— 只藏内容，不藏存在，
  否则 AI 会以为整理完了，而用户看到窗口里还剩一堆没动的标签。
- 另提供一个「只发送域名」的严格模式，并在开关旁如实写明它会明显降低分类质量。
  它是给「我知道会变差但我就要」的人准备的，不是隐私的主线方案。

授权那一屏必须一次性说清：标签标题和地址会作为消息内容进入当前 AI 对话，
已经发出去的内容无法通过事后关开关收回。这句话说一次就够，不需要在每个开关旁边重复免责。

⚠️ 如果当前模型自己有联网能力，它可能自行访问这些链接。扩展不提供页面访问工具，
也无法阻止模型的自带能力 —— 这一句放在授权屏，不放在开关说明里。

本机账本保留完整地址（否则重开被关掉的标签无从下手）。发给 AI 的一切 —— 列表、预览、执行结果、
审计查询 —— 统一执行当前策略，包括错误消息（浏览器的错误字符串里可能带完整 URL）。

标题、URL、书签名称、以及模型联网取回的内容，全部是**不可信数据**：不作为指令、
不作为授权、不作为「用户同意了」的证据。prompt 里明写，后台也不解析它们做任何决策。

## 10. 工具协议

沿用 Agent 的字符串参数协议：`operations` 是 JSON 数组字符串，后台解析后逐项严格验证，
拒绝未知操作类型和多余字段。一批最多 30 个操作、涉及最多 500 个对象；
规划规模上限 2,000 个普通标签 / 10,000 个书签节点；列表每页最多 100 项。

| 工具 | 能力 | 档位 |
|---|---|---|
| `browser_list_tabs` | tabs.read | 读 |
| `browser_list_tab_groups` | tabGroups.read | 读 |
| `browser_list_bookmarks` | bookmarks.read | 读 |
| `browser_query_changes` | 按记录类型对应的读能力 | 读 |
| `browser_arrange_tabs` | tabs.arrange | 低损 |
| `browser_manage_tab_groups` | tabGroups.write | 低损 |
| `browser_arrange_bookmarks` | bookmarks.arrange | 低损 |
| `browser_close_tabs` | tabs.close | 有损 |
| `browser_delete_bookmarks` | bookmarks.delete | 有损 |
| `browser_restore_state` | 按被恢复状态的种类，取 `tabs.arrange` / `bookmarks.arrange`（+ 有组则 `tabGroups.write`） | 低损 |

⚠️ **有损操作是独立的工具，不是某个工具的一个 operation type。** 这样档位可以直接从工具名读出：
权限注入是 1:1，批准 UI 不需要先解析 `operations` 才知道该不该提供「本次任务放行」，
而「把 5 个关闭混进一批移动里」在协议层就不可能发生。工具名同时也是 prompt 里最显眼的标记，
比藏在 JSON 里的 `"type":"close"` 更难被模型忽略。

⚠️ **`browser_restore_state` 花的能力是它自己要用的那个，不是原批次的。** 恢复一批「关闭」
要做的事是重开并摆好标签，那是 `arrange`；为了把一次关闭放回去而去要 `tabs.close`，
要的是错的东西。所以恢复批次落库时 `tool` 记的是 arrange 工具，档位和权限检查
都走和别的批次同一条路，没有分支。

⚠️ **这张表的 schema 由 `mcp/providers/browser-provider.ts` 提供，进 prompt 的那段是
`mcp/schema-generator.ts` 自动生成的**，不是手写的一大段字符串。手写会让
`<bs_agent_tool>` 的格式说明在项目里长出第二份，然后和真的解析器对不上。

上表里没被授权的行不会出现在 prompt 里（`promptTools()`），但**仍然注册着** —— 前者是为了别让模型
调一个必然被拒的工具，后者是为了重载会话时还能从对话里的调用反推出这是 Browser agent。

读工具的形态：

- `browser_list_tabs`：默认**所有窗口**（`window_id` 省略或 `"all"`），传数字只看一个窗口；
  `limit`/`offset` 分页。宿主窗口排最前，同一窗口内按 index 排，分页不会把两个窗口交错。
  每项含 `id`、`title`、`url`、`window_id`、`group_id`、`pinned`、`active`、`protected`、
  以及 §8 的 `duplicate_of` / `similar_to`。另带 `windows` 摘要：`window_id`、
  `kind`（`normal` / `app`）、`host`、`tab_count`。
  ⚠️ 以前默认宿主窗口，这就是「多窗口识别不到」的根因：模型拿不到其它窗口的 id，
  而 Gemini PWA 的宿主窗口里只有对话本身。
- `browser_list_tab_groups`：同样默认所有窗口，每个组带 `windowId`。

非 `normal` 窗口（PWA、popup）一律报成 `app`。Chrome 在这类窗口里不能移入/移出标签、
`tabs.group` 会把标签悄悄拖进某个普通窗口、`tabs.create` 指向它会落到别的普通窗口——
所以 prepare 阶段（`checkWindowKinds`）直接拒绝，`create` 不指定窗口时宿主若是 app 窗口
就落到最近聚焦的普通窗口。
- `browser_list_bookmarks`：按 `parent_id` 读一层，或按 `query` 搜索。**不返回整棵树。**
  根节点 ID 由扩展解析后提供，AI 不需要也不允许硬编码（见 §12）。
- `browser_query_changes`：分页列出本机批次，每条带 `can_restore_before` / `can_restore_after`；
  带 `batch_id` 时额外返回逐步的操作和状态。不返回快照，不接受 SQL。
- `browser_restore_state`：`batch_id` + `side`（`before` 默认 / `after`）。见 §11。

## 11. 本机账本与恢复

账本记的是**扩展让浏览器经过的那些状态**，不是它调用过的那些操作。这一句决定了下面所有东西。

存在**业务 SQLite 里**（`browser_agent_batches` + `browser_agent_steps`），跟着当前 profile 的库走。
两张表都不在 `SYNC_TABLES` 里，所以不进 Drive 同步；本机整库导出会带上它们，由保留策略限制体积。

```
批次头   id / owner_tab_id / epoch / tool / operations / created_at / status / error
         before_state / after_state          ← 两个全量快照
         restore_of / restore_side           ← 这条批次是「把某个状态放回去」的话，指向来源
每一步   operation / status                  ← 只有判决，没有快照
```

⚠️ **一个批次两份快照，一步零份。** `before_state` 和 `after_state` 是全量的（所有非隐身标签
和标签组，或者整棵书签树），它们就是账本存在的理由：detail 视图画的是它们，恢复就是把其中一份写回去。
步骤行只回答「这一步落了没有」——这是让一个跑到一半的批次可读的东西，
而它不需要快照。三十步的批次因此存 2 份快照而不是 31 份。

⚠️ **`after_state` 失败时也写。** 一个中途停下的批次把浏览器留在了谁都没计划过的状态里，
而这份快照正是让那个状态可读、可回退的东西。只有「一步都没跑」时才不写 ——
那种情况 `before` 已经描述了浏览器。所以「有没有 after」也就等于「它到底动手了没有」。

⚠️ **不为它单开数据库。** 单开的代价是第二套存储引擎：没有 migration 机制、没有保留策略。
它能换来的是把账本放在 `execute_sql` 够不到的地方，而那件事并不需要防
——agent 没有任何动机去删自己的审计痕迹，插件其它任何地方也不是按「它可能会」设计的。
`journalReady()` 会顺手 `deleteDatabase` 掉遗留的 `browser-agent-local-v1`。

⚠️ **落盘只走窄口。** 仓库层（`operations/browserAgent.ts`）对外是
`insert` / `patch` / `insertStep` / `setStepStatus` / `snapshots` / `list` / `listSteps`，
没有 `save(batch)` —— 一次写一行。handler 内存里仍然拿一个完整 `Batch` 当工作模型。
`snapshots()` 单独一个查询，因为两棵树是这张表能交出的最大的东西，旁边的历史列表不该为它买单。

⚠️ **设置不在这里。** 权限与 URL 开关放 `chrome.storage.local`——它是 Chrome
配置文件级的事实，而且权限窗口没有 tab、也就没有对应的 profile 数据库，不能被挡在数据库打开后面。

⚠️ **账本跟着 profile 数据库走。** 两个 tab 登录不同账号就是两份账本，
`ensureDbForTab(owner)` 保证一次请求落在它自己那个 tab 的 profile 上。
换账号后查不到旧记录，但不会写错地方。

保留策略：最近 200 个批次。这是唯一一张没有用户动作给它封顶的表，而每行带两个全量状态
——让账本有用的东西同时也是让它变大的东西。200 是对着账本的用途选的：
把刚出错的东西放回去，以及几天后回答「我的标签当时怎么了」。两件事都够不到 200 个批次之前。

### 状态与异常

`prepared → applying → applied | failed | unknown`。执行前必须先持久化 `prepared`，
持久化失败就不执行。所有前置检查在 `applying` 之前跑完（§4、§7）：过不去就是**拒绝**，
记 `failed` + 原因、不写 `after_state`，而不是记成一次半途而废。
调用浏览器 API 前写 `applying`，成功后写 `applied`。
API 结果或持久化结果不明确时写 `unknown` 并**停止**，不自动重试。
后台重启后发现残留的 `applying`，标为 `unknown` 并保留证据。同一个 planId 不重复执行。

写入串行（一次只跑一个批次），**但读不进这个队列** —— 一次 10,000 节点的书签 prepare
不该把列表查询堵住。一步失败就不开始下一步，已成功的步骤保留，返回逐项结果。
「停止」只承诺不发起下一次调用，不承诺中断已发出的调用，也不自动回滚。

### 恢复：加性，这就是全部约定

把一份记录下来的状态放回去 —— 不见了的对象重建出来，挪走的搬回原位，名字和颜色重新设上 ——
并且**永不删除任何东西**。现在存在、而快照里没有的对象，连同它的内容原样留着，
最后排在被恢复的对象之后。

⚠️ 这不是给「精确恢复」打的折扣，是换掉了默认值。让浏览器**等于**一份快照，
意味着关掉用户之后开的标签；而「把我的标签放回原来的样子」不是「把我这十分钟的浏览作废」的请求。
它同时也意味着恢复永不删除，于是：

- 恢复的档位是常量 `low`，不需要逐 plan 判定。
- 同一个状态可以反复恢复，结果一样，所以**不存在「已经撤销过」这种状态**，
  也不需要 `undone_by` 这类一次性额度。
- 一个批次的两份快照都可以恢复，`before` 和 `after` 各一个入口。

代价必须写在卡上，不能藏：结果是**那棵树 + 之后新增的东西**。`RestoreEffects.extra`
就是那个数字，缺了它用户会把树读成「我的浏览器最后就长这样」，而那是它唯一不承诺的事。

⚠️ **id 没了就认领长得一样的。** 重建一个对象会给它新 id，所以第二次恢复同一个状态时，
记录里那个 id 又找不到了 —— 不认领就会再造一份副本，用户自己手动重开的标签也会被复制一遍。
标签按完整 URL 认领，书签按标题 + 地址认领，各只认领一次（快照里两个同址标签仍然要两个标签）。
这条是「反复恢复收敛到同一处」的唯一实现方式。

⚠️ **预览和执行必须用同一次遍历算。** `resolveRestore()` 一次算出「记录里每个对象现在是谁」，
`inspectRestore()` 从它产出树上每个节点的 `effect` 和旁边的计数，`restoreTabs()` 从同一个结果
执行（含 §8 的游标、含上面的认领）。一个用另一套模型算出来的预览，就是一个会说谎的预览。
宿主闸门（§13）也放在这里，于是预览能在用户批准前就拒绝，commit 也会对着当下的浏览器再查一遍。

#### 跨浏览器重启：id 换一套，对象还是那些对象

标签、窗口、组的 id 都是**每次浏览器运行重新发的**，重启后不但记录里的 id 找不到，
还可能指到另一个对象上。所以恢复不靠 id 判定「同一个」，而是分三种对象各有一套认领方式：

| 对象 | 同一 session（`epoch` 相同） | 跨重启 |
|---|---|---|
| 标签 | id 命中即是 | 按完整 URL 认领；认不到就按地址重开 |
| 窗口 | id 还在即是 | **没有任何东西能认出一个窗口** —— 宿主标签所在窗口对应记录里宿主所在的那个，其余一律新建 |
| 组 | id 还在即是 | 按成员认领：映射后的成员如果都在同一个现存组里就是它，否则新建 |
| 书签 | id 跨重启稳定，一直可用 | 同左 |

⚠️ **窗口是唯一「没有特征」的对象**，所以它只有两个答案：session 内的 id，和宿主标签那个窗口
（宿主本来就不允许离开它，§13）。其余窗口按记录里的窗口顺序**新建**，由该窗口记录里的第一个标签
建出来（`windows.create` 要么给它一个标签搬进去、要么给它一个地址打开），而不是先建空窗口再关掉
New Tab —— 恢复永不关任何东西。

⚠️ **同 session 的 id 命中优先于宿主锚点。** 否则用户把侧栏挪到别的窗口之后，
记录里宿主那个窗口会把它名下所有标签一起拖过去。这种情况按 §13 直接拒绝，不是「凑」一个结果。

其余规则：

- 书签重建先建父再建子（快照是前序遍历，天然满足），过程中维护新旧 id 映射。
- **恢复成功后不留自己的记录。** 账本回答的是「扩展改了我的浏览器什么」，把一份记录放回去
  是这个问题的答案，不是它的又一个实例；一次撤销留一行会让列表里每条记录旁边多一条它的逆，
  各带两份全量快照去挤 200 条的上限。「再改回去」仍然是一次点击：来源批次的两份快照都还在，
  换成恢复另一边就是了。⚠️ 只有落地干净的才删 —— `failed` / `unknown` 的恢复把浏览器留在了
  谁都没计划过的状态里，那一行是它唯一的证据。
- 宿主标签允许在窗口内被重排（别的标签要回到记录位置就得让它动），也允许恢复它的固定状态
  （那是标签自身的属性，不是它待在哪儿）。**窗口和组这两条按 §13 各有各的答案，判定都用
  映射之后的目标、不是原始 id**：
  - **窗口不一致 → 拒绝整批。** 只可能是用户把侧栏挪到了别的窗口，而这条没法「跳过」——
    记录里同窗口的其它标签全都要去一个宿主不在的地方。
  - **组不一致 → 跳过宿主这一条，其余照常恢复。** §13 说宿主根本不在整理范围内，
    那「快照要求它在某个组里」对它就是一条不适用的要求，而不是一个要停下来的冲突。
    宿主从组成员名单里剔除（本来就在里面时剔除也没差别），只有它一个成员的组直接不建。
    ⚠️ 卡上必须写一行说明：树把宿主画在那个组里，而它是这棵树唯一会说错的一行。
    之前这里是拒绝，代价是「宿主当时在组里 + 重启后那个组没恢复」这种再普通不过的情况下，
    整条记录都变成不可恢复 —— 拒绝的理由和用户想要回来的那些标签毫无关系。
- 记录里某个页面不是 http(s)、扩展打不开，停止并说明，绝不改动其它对象来「凑」一个位置。

### detail 视图：两棵树，各带一个入口

历史列表里一条记录点开，是这个批次前后两个状态，各画一棵树，各有一个「恢复到这个状态」。
点了之后同一个面板换成那次恢复的预览（树上标注了这次会动哪些节点）+ 批准按钮 ——
同一棵树，第二个阶段，所以被批准的和刚才点的是同一个东西。

⚠️ 树是唯一能回答「我的浏览器当时长什么样」的形态，也是唯一能举起来和旁边真实浏览器逐眼对比的形态。
它顺带消灭了最后一个要提 id 的地方：父容器是树上一个看得见的节点，不是一个要拿数字代指的东西。

⚠️ 树走 `{ action: 'trees' }`，不走 `browser_query_changes`。AI 需要 id 才能操作，
而树刻意没有 id。它做的是同一套能力检查、过同一套脱敏，所以「面板能看什么」
仍然等于「agent 能看什么」。

## 12. 跨浏览器行为差异

API 有无由 §2 的探测解决。这里是**同名 API 行为不同**的地方，它们会影响前置条件的写法
和预览里的承诺措辞。

| 差异 | Chrome | Firefox | 本方案怎么做 |
|---|---|---|---|
| 新建标签的地址 | 未提交前在 `pendingUrl` | 没有 `pendingUrl`，`url` 是 `about:blank` | 地址取 `url \|\| pendingUrl \|\| ''`；正在导航的标签不参与地址比较（§7） |
| 给固定标签分组 | 报错 | [自动取消固定](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/tabs/group)后再分组 | 扩展自己先拒绝，两边行为统一，预览里说明「固定的标签不参与分组」 |
| 折叠含活动标签的组 | 活动标签被移出组 | [活动标签保持可见](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/tabGroups/update)，其余折叠 | 不折叠包含当前活动标签的组；AI 要求折叠时降级为「已建组但未折叠」并在结果里说明 |
| 组 id 跨重启 | 可能变化 | [恢复后可能变化](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/tabGroups/TabGroup) | 一律靠 `epoch` 判定 id 是否还可信；不可信时组按成员认领、窗口新建（§11） |
| 收藏夹根节点 ID | `'0'`、`'1'`、`'2'` | `'root________'`、`'toolbar_____'` 等 | 一律 `bookmarks.getTree()` 解析后使用，代码和 prompt 里都禁止硬编码 |
| 书签节点类型字段 | 无 `type` | 有 `type` | 判断目录一律用 `url === undefined` |
| 分屏标签 | 无 | 149+ 有，分组/取消分组一半会带上另一半 | 同一 `splitViewId` 的标签在前置条件和预览里视为一体 |
| 私有 / 隐身 | 扩展默认不进 | 扩展默认不进私有窗口 | 一律过滤，不返回也不可操作 |

⚠️ 「扩展自己先拒绝」这个做法在上表里出现两次（固定标签分组、折叠活动组）。
理由一致：**两个浏览器都能跑，但结果不一样的操作，是最糟的一类**。
预览必须能对结果说话，而它没法同时对两种结果说话，所以取更保守的那一边并明确告知。

Firefox for Android 没有标签组、窗口模型也不同。能力探测会自然关掉组能力，
不为它做额外适配，也不宣称支持。

## 13. 宿主标签与 UI

跑 Agent 的那个标签（Gemini / AI Studio 页面）**不在整理范围内**：

- `browser_list_tabs` 里标 `protected: true`，prompt 里说明它不参与整理。
- 任何操作不得关闭它、移动它、把它移出或移入组。AI 发起的操作直接拒绝；
  恢复是把这条当成「不适用」而不是「冲突」——组归属跳过、窗口不一致才拒绝（见 §11）。
- 它所在的组允许改名改色，不允许折叠（见 §12）、不允许移动。
- 预览里显式写一行「当前这个标签不参与整理」。用户会数标签，
  少一个不解释就是一个 bug 报告。

⚠️ **宿主标签导航不取消正在执行的批次。** Gemini 是 SPA，用户切一个对话就是一次地址变化；
把地址变化当取消信号会让批次莫名中断在中途。批次归属靠 `planId` + owner tab id，
而导航不改变 tab id。只有宿主标签**被关闭**才取消（此时结果无处可回传）。

UI 分工沿用 Agent 现有的三处，不新建路径：

| 位置 | 内容 |
|---|---|
| Agent Tab | AgentSwitcher 里的第三段、权限设置入口、本机记录与恢复入口（§11 的两棵树） |
| `>` 弹层 | **一行**「Browser Agent」；权限没给时那一行的描述换成提示，点它直接开权限设置 |
| 聊天流卡片 + Dock | 预览与批准，两处同一个 resolve，谁先答谁算 |

⚠️ **`>` 里只有一行。** 「整理标签页 / 管理标签组 / 整理收藏夹」这类子项各自只是往 prompt 里
塞一句 `focus`，看着像几个选择，可对「这件事跟你的哪样东西有关」给出的是同一个答案 ——
而那几句话用户自己打得出来。旧的 agent id 仍在 `LEGACY_AGENT_IDS` 里解析，
这样重载一段老会话不会认不出它属于谁。

运行期间禁止切换 Agent。Browser Agent 只拿到 `builtin-browser` 这一个 server 加上共享的
`builtin-core`（`complete_task` + `activate_skill`），归属检查在 `mcp/registry.ts`，
和另外两个 agent 走同一套 —— 没有「Browser 专用」的分支。权限设置是独立扩展窗口
（`permissions.request()` 需要用户手势，且它不能是 AI 可触发的动作）。

代码落在哪，见 `agent-loop-architecture.md` 的「加一个 agent 要碰的地方」。要点是**没有
独立模块**：soul 在 `prompts/souls/browser-soul.ts`，工具在 `mcp/providers/browser-provider.ts`
+ `tools/browser-tools.ts`，领域状态在 `agent-loop/browser/`，面板在 `agent-tab/browser/`。

## 14. 实施顺序与验收

1. 能力探测 + 权限设置窗口（Chrome / Firefox 同一份实现）
2. 读工具 + 排除清单 + 重复标记
3. 对象级前置条件 + 相对锚点 + 低损写入 + 结果导向预览
4. 本机账本（双快照）+ 保留策略 + 加性恢复 + 两棵树的 detail 视图
5. 有损工具 + 「待清理」默认路径 + `sessions` 重开
6. Firefox 真机验证

### 正向验收（这些不过，功能就是不可用）

- 一个 84 标签的窗口，用户**在整理过程中继续正常浏览**（开标签、切窗口、读页面），
  整理能一次走完，不出现失败。
- 预览一屏之内看得懂：说得出会新建几个组、多少标签被动、有没有东西被关掉、多少标签不动。
- 历史记录点开能看懂整理前后各是什么样，点一次「恢复到这个状态」+ 一次批准就回去了。
- 恢复之后，用户在整理之后新开的标签**一个都没少**，并且预览事先说了有几个。
- 同一个状态连续恢复两次，第二次不产生任何副本。
- 重复标签能被识别、归入「待清理」，用户一次操作完成清理。
- Firefox 139 上以上流程与 Chrome 表现一致；Firefox 138 上组能力整体隐藏并说明原因。

### 安全验收

- 能力默认全关；撤销权限后对应读写立刻失败。
- 有损操作在任何设置下都逐批批准；低损的「本次任务放行」不泄漏到有损批次。
- 批准绑定 plan；旧 plan、不同宿主、点名对象已消失一律失败，并记为 `failed`（无 after 状态）。
- 关闭绑定 URL：预览之后目标标签导航走了，这一批被拒绝，什么都不动。
- 恢复永不关闭标签、永不删除书签，无论快照与现状差多少。
- 中断后不重复创建/删除，失败明细可查，`unknown` 不自动重试。
- 排除清单命中的对象不出现在任何发给 AI 的内容里；严格模式下不出现完整地址；
  错误消息和两棵树同样脱敏。
- 账本不进 `SYNC_TABLES`（不上 Drive）；本机整库导出会带上，由保留策略封顶。
- 跨浏览器重启不使用旧标签/组 id，此类批次可查看不可恢复。
- 宿主标签在任何批次里都不被关闭；不被移到另一个窗口或另一个组；宿主导航不中断批次。

### 必须人工真机跑的清单

模拟 API 测不到的都在这里，而这个功能的失败模式几乎全在这里：

- 边整理边开新标签 / 关标签 / 切窗口 / 让页面加载完成
- 整理中途刷新宿主页面；整理中途在 Gemini 里切到另一个对话
- 关闭标签后立即恢复，以及等浏览器淘汰了最近关闭条目之后再恢复
- 整理之后手动开一批标签、固定其中一个，再恢复整理前的状态（检查游标和 `extra` 计数）
- 含固定标签、含分屏（Firefox 149+）、含受管理书签的窗口
- 折叠一个包含当前活动标签的组（Chrome 和 Firefox 分别验证）
- 浏览器重启后查看旧批次（标签类应可查看、不可恢复；书签类可恢复）

自动化测试 `node --test scripts/test-browser-agent.cjs` 覆盖协议验证、档位推导、
前置条件判定、锚点换算、脱敏、账本状态机、加性恢复与幂等。它保证逻辑，不代替上面的清单。
